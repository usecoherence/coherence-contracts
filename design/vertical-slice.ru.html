Один spec. Все AC. Код. Прогон. Отчёт.

Минимальный контракт, который покрывает вертикальный путь целиком и ничего сверх него. Таблицы — это JSONL-строки в git. Protobuf описывает строку, а не ORM. Всё, что не нужно этому пути, вынесено за границу слайса.

01Authorspec + AC + owner в JSONL
02Ingestrepo → branch → file
03LinkAC —verified_by→ file
04Selectlinks → run plan
05Executebehavior engine → artifacts
06Reportevidence → сигналы → persist
contracts.jsonl versioned · deterministic order
spec acceptance_criterion owner code_repo repo_branch code_file scip_symbol scip_link link
источник истины (git) artifact bundle (gitignored, inspectable) ядро контракта

В слайсе

  • +Один spec со всеми AC и владельцем.
  • +Ingest списка репозиториев и веток из конфига.
  • +Ручная или агентская связка AC —verified_by→ code_file.
  • +Детерминированный выбор: links → run plan.
  • +Один behavior: run_tests(files); artifacts в run/.
  • +Отчёт по каждому RunItem; --persist решает, что публикуется.
  • +Пример расширения: Confluence-страница через persisted_to.

Отложено осознанно

  • −ObjectKindDefinition и Any-envelope: не нужны, пока объекты третьих сторон не появляются в runtime.
  • −Протоколы валидации: в слайсе валидация — это вывод тула и exit code.
  • −Entity / Attribute / State / Transition / Invariant — вне пути.
  • −Глубокий SCIP-ingest: таблицы зарезервированы, связи — на уровне файлов.
  • −Много behavior-движков: один, но точка расширения видна.
  • −Jira/GitHub-публикаторы: паттерн доказан одним Confluence-примером.

Схема

Три пакета, четырнадцать сообщений. Строка таблицы — это message с общим RecordMeta; связь любых двух строк — один Link.

coherence/kernel/v1/kernel.proto~30 строк
syntax = "proto3";
package coherence.kernel.v1;

// Общая идентичность и отображение для любой строки.
message RecordMeta {
  string id    = 1;  // стабильный, не переиспользуется
  string slug  = 2;  // человеческий handle
  string title = 3;
  string description = 4;
  string status = 5; // draft | active | archived
  int64 created_at_unix_s = 10;
  int64 updated_at_unix_s = 11;
  map<string, string> annotations = 20;
}

// Одно направленное семантическое ребро между строками.
message Link {
  string id = 1;
  string type_from = 2;  // "acceptance_criterion"
  string from_id   = 3;
  string type_to   = 4;  // "code_file"
  string to_id     = 5;
  string relation_kind = 6; // "verified_by"
  string note = 7;
  double confidence = 8;    // 1.0 authored, <1 inferred
  int64 created_at_unix_s = 10;
  int64 updated_at_unix_s = 11;
}

Решения, которые делают схему маленькой

РешениеПочему
Один RecordMeta на все таблицыid / slug / title / description / status / время описываются один раз, а не в каждом message.
Один Link вместо edge-таблицverified_by, depends_on, persisted_to — строки одного вида, без отдельных message на каждую связь.
Канонические имена — singulartype_from / type_to совпадают с именами таблиц и message: spec, acceptance_criterion, code_file. Один словарь вместо двух.
Никакого Any и реестровJSONL уже типизирован именем таблицы. Реестр kinds вернётся, когда появятся runtime-объекты третьих сторон.
Расширения — отдельные пакетыConfluence/Jira добавляют таблицы и линкуются к core через Link. Core не меняется.

Граница пакетов проверяема: coherence.kernel.v1 не импортирует coherence.core.v1. Это правило уже зафиксировано в AGENTS.md и покрывается buf-плагином.

Результат

contracts.jsonlодна строка = одна запись
{"table":"spec","id":"spec-001","slug":"specs-as-code","level":"module","status":"active","title":"Specs as code","description":"...","owner_id":"owner-001"}
{"table":"acceptance_criterion","id":"ac-001","spec_id":"spec-001","slug":"ac-jsonl-roundtrip","status":"active","title":"JSONL roundtrip"}
{"table":"owner","id":"owner-001","name":"core"}
  • 1Детерминированный порядок: (table, id). Diff читается, merge предсказуем.
  • 2Уникальность: id глобально, slug — в пределах таблицы.
  • 3Ссылки проверяются при чтении: owner_id и spec_id должны существовать.
  • 4Ошибки — список {line, table, id, problem} и exit code 1.

Один файл — осознанный старт. Когда объём вырастет, разбиение на contracts/spec.jsonl и т.д. — механическая операция, схема не меняется.

Выбор полностью детерминирован: никакого LLM в момент прогона. Агент может предлагать links, но выполняются только записанные рёбра.

Progressive disclosure

  1. 1Сломанный AC: текст и id. Самое важное — первым.
  2. 2Файл и диапазон строк; сниппет под спойлером.
  3. 3Контекст: соседние символы, другие файлы, соседние AC — свёрнуто.
  4. 4Воспроизведение: screenshot / recording / trace + команда re-run.

Принцип: отчёт должен читаться за 30 секунд, а раскрываться до полного debug-контекста только по запросу. Evidence пре-процессится под эти четыре уровня.

Persist policy

Один и тот же прогон ведёт себя по-разному в зависимости от контекста и флага. Переключи:

Чтоlocalci+ --persist
artifact bundle в run/дадада
report-строки в contracts.jsonlнетдада
внешние копии evidenceнетдада
PR comment / статуснетдада

local по умолчанию: артефакты лежат рядом, но ничего не публикуется.

Publish — composition

spec persisted_to → confluence_page ⇒ upsert_page(spec)

Публикация не добавляет полей в Spec. Она добавляет таблицу расширения и ребро. Тот же паттерн — Jira, GitHub, HTML-сайт.
